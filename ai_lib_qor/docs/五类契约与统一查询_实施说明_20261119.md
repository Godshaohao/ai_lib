# 五类契约与统一查询：实施和兼容说明

本说明对应《五类核心契约、统一查询与增量消费实施规格》，以当前实现为准。查询读取 work 中的已归档记录，不因为打开页面或获取来源矩阵而扫描 RAW；显式运行检查时才读取选中的文件。

## 数据职责与既有格式

| 业务职责 | 产生与主要持久格式 | 读取及消费 |
| --- | --- | --- |
| DeliveryRecord | RAW 登记写入 `delivery_record.v1`，扁平目录 `delivery_*.json` | `SourceRepository`、`LibraryDataQuery`、有效版本、检查适配器；`raw.simple.v1` 是查询投影 |
| FormalSnapshot | Formal 同步写入 `formal_snapshot.v1/v2`，`formal_<NL>_*.json` | 查询、正式来源对照及有效版本初始化；`formal.simple.v3` 是投影，保留实际 `link_target` 或未记录状态 |
| EffectiveVersion | 原有 `effective_version.v1` 或可直接发布的 `effective.simple.v2` | 版本查询、来源差异、时间线、检查适配器；v1 历史保持可读 |
| FileFacts | 对明确选中的 LEF/Liberty 调用现有 Parser，写入 `file_facts.v1` | 现有检查插件与报告，记录来源引用、解析器和覆盖范围 |
| CheckResult | `checks/assembler.py` 汇总检查，写入 `check_result.v1` | 现有 HTML、Excel 和运行记录 |

过去另外单列的 EffectiveIndex 是可重建索引；AcceptanceEvent 是已发生的人工采纳记录，二者继续兼容，不是新增核心数据。`latest_*` 仍为相对软链接而非新 JSON 契约。`evidence_delivery_*.json` 是扫描及分类辅助记录，不应当作为普通来源列表的权威来源；旧文件和真实采纳历史不会被清理。

## 查询与增量检查

`application/data_query.py` 的 `LibraryDataQuery` 是共享入口。`list_deliveries` 使用已确认的配置顺序、已确认的日期规则或旧证据，不用登记时间猜测顺序；`get_file_history` 按 View 和相对路径查每个文件出现在哪些交付。`get_effective_files` 支持旧版及新 v2 记录，`compare_revisions` 和 `file_timeline` 复用 `effective_json.py`；`get_changed_file_pairs` 通过历史 Delivery 定位旧、新文件，仍不打开源文件。`compare_formal_vs_effective` 将 Formal 的实际链接记录和已解析的 RAW 来源与有效版本对照。

`SOURCE_CHANGED` 表示来源变化，尚未进行内容检查；`NOT_CHECKED` 不代表内容一致。来源不存在、身份未确认、跨供应商旧引用不唯一时，不生成伪造的检查结论。

Formal 对照的 `verification_scope=ARCHIVED_RECORDS_ONLY` 明确表示这是归档记录对照，不会重新读取当前链接。`archived_path_status=MATCH` 只表示快照的已记录 `resolved_path` 与 Delivery 中 `source_root + relative_path` 的路径文本一致；`MISMATCH_OR_INDIRECT` 表示不一致或可能存在中间软链接，无法离线判定，来源关系标为 `UNKNOWN`。真正的链接文字与最终目标核验发生在显式 Formal 同步时，且仅证明同步时的链接关系，不证明文件内容一致或现在链接仍未变化。

CLI 例子，环境中需安装 `requirements-pipeline.txt`：

```bash
export PYTHONPATH="$PWD/src:$PWD/../src${PYTHONPATH:+:$PYTHONPATH}"
python3 -m ai_lib_qor data-query --work /path/to/work --kind changed-pairs \
  --vendor SRAM22 --library sram22_256x16m8w8 --set-id sram22_256x16m8w8 \
  --revision rev_0001 --other-revision rev_0002
python3 -m ai_lib_qor run-changed-lef --work /path/to/work --runs /path/to/runs \
  --vendor SRAM22 --library sram22_256x16m8w8 --set-id sram22_256x16m8w8 \
  --before rev_0001 --after rev_0002 \
  --pin-liberty-path LIB/NLDM/example.lib
```

第二个命令显式选择当前有效 Liberty 才运行 LEF–Liberty Pin 检查；只支持唯一的变化 LEF 与指定 Liberty，未选择时仅执行变化 LEF 的 Macro/Pin 比较。报告明确声明范围，并不代表完整 IP 检查。每次运行保存一份 CheckResult 和现有 HTML/Excel；Facts 可在单次调用内复用，跨运行的持久缓存尚未实现。

## Evidence 和兼容边界

无 Evidence 时，`SourceRepository` 对历史文件身份给出 `UNKNOWN`、排序给出 `UNCONFIRMED`；普通来源查询仍可从已归档 Delivery 提取路径和 View。显式配置的交付顺序或已确认日期规则可支持最新/次新和 latest 链接；无法确定时不猜测。旧的检查适配器仍需要旧 `file_id`、`file_key` 与已确认的身份，因此不能直接删除 Evidence 读写。新同步暂时仍写 Evidence；缺失旧扫描元信息的相同版本重跑标为 `unverified`，不误报原地修改，也不重复发布。不能据此声称检测过原始文件变化。

历史 `delivery_id` 不改名，已有 index、采纳记录和链接不删除；`effective.simple.v2` 发布仍走现有校验和发布器。Formal 的旧记录如果没有 link 文本，保持未记录，不根据路径补造。

## 验收样例与已知限制

`exports/contract_query_demo_20261119/` 是隔离模拟样例，包含来源查询结果、模拟 LEF/Liberty 和一次检查运行。Rev001 与 Rev002 各有七个归档成员：两个来源变更、五个沿用。模拟文件实际只为所检查的 LEF 和 Liberty 准备；其余五个条目仅用于验证归档来源查询，不能声称其内容被读取。该样例 Formal 数据是复制的既有历史快照，不是这次对模拟目录重扫的结果，快照中的原始 `link_target` 不应解释成指向模拟文件。样例中的身份确认为测试构造，不代表生产确认。

这次只将有效版本页的 A/B 来源表接入共享查询，并保留现有检查工作台。其他页面和 Excel 的全部来源映射尚未逐一消除原有逻辑；当前运行检查只覆盖上述 LEF 对比及可选单组接口检查，尚不自动比较变化 Liberty 的旧/新内容，也未完成任意多对组合和整体 IP 报告的新链路。旧流程仍可使用现有检查计划。未执行生产 RAW/Formal 大规模性能和浏览器人工视觉验收。

2026-11-19 补充：原 `contract_query_demo_20261119/query_results.json` 是旧版本生成的静态结果，其中 Formal 与模拟 Delivery 的根路径不一致，不能用其中的 `SAME_SOURCE` 证明模拟链接匹配；请改看同目录下 `formal_comparison_corrected.json`。新增 `scripts/formal_link_verification_demo.py` 可在指定的全新目录生成独立模拟 RAW 和真实符号链接，通过现有 Formal 同步实际采集、验证并发布快照。`exports/formal_link_verified_20261119_v2/verification.json` 是一次执行结果；其中的链接核验发生在生成时，不代表生产数据验收。
