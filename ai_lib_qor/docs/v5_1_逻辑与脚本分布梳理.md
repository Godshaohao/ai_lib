> 梳理日期：2026-11-13。依据 v5.1 补充包、工作区中的 v3/v5 设计包，以及 `../src_qor` 的 README 和部分源码。这里区分已有代码、合成原型和建议流程；未声称已完成生产迁移。

## 1. 一分钟理解

目标是让工程师针对选定的库文件，能够追溯交付与正式来源，比较 LEF 文件变化，检查 LEF 与 Liberty 的对应关系，并查看有依据的报告。v5.1 提出：固定本次输入和检查范围后，复用已有脚本，把检查贡献统一整理，核对证据，再按已确认的 v3 契约组装结果并交给报告读取。

四件事应分别表达：**来源发生变化、文件内容发生变化、质量检查结论、人工采纳版本**。现有 `review_result.v1` 和 v5.1 拟产出的 `check_result.v1` 是不同结构；不能因名称相似认为读取链已接通。v3 七份 Schema 已复制在本工作区，但它们源自设计包，是否与实际生产权威契约一致仍需项目确认。

## 5. v5.1 的提议结构

文档提出 `src_qor_next/` 下设置 `contracts/`、`runner/prepare_inputs.py`、`runner/assemble_check_result.py`、`runner/evidence_guard.py`、`adapters/lef_compare.py`、`adapters/lef_liberty.py`、`presentation/` 和 `cli.py`。这是**提议目录**，本次检查没有发现补充包实现这些新模块；不应从目录图推断已有可运行流程，也不要求照图一次性创建全部文件。

新增的证据门禁可借鉴补充包中的原型，但不能把原型直接当成已完成的正式门禁。提议中 `Contribution` 与 `CheckPlan` 为内存或暂存中间态，正式结果应先完成字段映射和 v3 校验。

## 6. 合同与增量边界

- v5.1 拟保留 v3 的七类契约；检查结果目标为 `check_result.v1`。v5 示例 `check_run.v1` 的 `checks` 不能直接替代 v3 的 `file_changes`、`quality_checks`；指标、范围和证据是否能无损表达需要逐字段确认。
- v5 中 `PARTIAL` 与 v3 中 `INCREMENTAL` 不自动等价：需要先确认交付覆盖、继承与删除语义。
- 同一 Revision 可运行多次检查。首版建议重跑受影响检查、保留旧 Run；当文件、工具和环境身份可可信确认后，再评估结果复用。
- 正式 NL 快照、最新计算 Rev、人工采纳 Rev 是不同事实；质量检查或报告更新不应自动变更 Rev 或采纳记录。

## 7. 补充包验证结果与未解决问题

在临时副本中执行 `python3 -m unittest -v test_evidence_guard`：9 项测试通过，证明所列合成场景下的原型行为。另作一项合成反例：将 Gate 的 `input_refs` 改成清单中的普通 `file_facts` 引用，同时将 `depends_on` 改为不存在的检查和指标，`verify()` 仍接受。代码中只有 `check_metric` 分支会检查上游指标，而 Gate 的后续检查仅要求一个输入引用和非空依赖。因此这个原型还不足以保证所有 Gate 都指向有效测量。

上述验证不代表已完成真实 RAW / NL / EDA 检查，也不代表已接入 v3 Schema。未修改补充包或现有运行仓库。

## 8. 建议先后顺序

1. **M0 合同核对**：确认工作区 v3 Schema 是否为项目权威版本；逐字段列出 v5 → v3 映射、缺失数据和无法无损表达的项目。
2. **M1 一个真实检查**：选一对真实 LEF 文件，复用现有比较能力，确认来源、输出及必要证据；先修正并验证门禁原型的已知反例。
3. **M2 两类检查汇总**：在同一固定目标下加入 LEF–Liberty，验证重复 ID、来源和覆盖，得到符合已确认合同的一次结果。
4. **M3 展示一致性**：用同一固定结果核对工作台 / HTML / Excel 的数字、检查状态和证据链接。
5. **M4 增量场景**：改变一个 LEF 或 Corner，检查影响范围，保留旧结果与版本历史。

M0–M4 是补充文档提出的验收顺序；本次没有执行真实项目里程碑。
