# 文件历史索引 v2

`file_index.json` 是由一个供应商／库内已归档 Delivery JSON 重建的派生索引，不是新交付事实，不记录 Effective、Formal、FileFacts 或采纳。文件按 View 和相对路径组织；`timeline` 与 `deliveries` 从新到旧，保存每次实际出现在 Delivery 中的身份及原始分类。未交付不表示删除，来源改变不表示内容改变。

2026-11-19 审查后：`deliveries` 的数组顺序是索引内唯一的业务顺序，不再重复保存 `delivery_order`、`file_count`；每次出现的 `version` 由 `delivery_id` 关联 `deliveries`。旧 v2 索引只有在全部旧字段与原归档记录完全一致时，才在下一次显式刷新时执行 `MIGRATE`；异常记录拒绝覆盖。当前样例为 `exports/file_index_review_20261119/file_index.json`。

## 自动登记

`sources/auto_ingest.py` 在既有 Library `.versions.lock` 内登记后调用 `refresh_library_index_locked`。只读归档 JSON，不读历史 RAW 文件内容。已有确认的 `delivery_orders`、已确认日期规则或历史 Evidence 指定的人工／配置顺序可用于排序；多个版本顺序未确认时返回 `ORDER_UNCONFIRMED`，不创建或覆盖索引。一个版本时顺序自然唯一。显式 `delivery_order` 不是默认可信：旧记录需有确认依据。

操作结果：`REBUILD` 首次建立；`APPEND` 新交付追加；`UNCHANGED` 不重写文件；`REORDER_REBUILD` 按已确认顺序重建；`ERROR` 表示索引损坏、旧历史引用缺失或归档内容变化等，保留已登记交付和旧索引并在登记结果中报告。扫描结果页面显示状态及原因。必要时应先检查历史和排序；人工确认后，独立构建命令的 `--rebuild` 可重建派生索引，不会改写 Delivery。

## 构建与读取

在 `ai_lib_qor` 目录执行，按本项目依赖环境设置 `PYTHONPATH`：

```bash
export PYTHONPATH="$PWD/src:$PWD/../src${PYTHONPATH:+:$PYTHONPATH}"
python3 -m ai_lib_qor.application.file_index \
  --input-dir /path/to/work/libraries/VENDOR/LIBRARY \
  --output /path/to/work/libraries/VENDOR/LIBRARY/file_index.json \
  --scan-sources /path/to/work/scan_sources.json
```

多次 `--input` 可选择分散的 Delivery，`--input-dir` 同时支持旧的 `deliveries/<id>/delivery.json`；`--order-ids id_new,id_old` 按新到旧指定完整真实交付 ID；也可显式使用 `--date-prefix-order` 或 `--trust-delivery-order`。后者表示使用者确认所有 `delivery_order` 是业务顺序；不能因为字段存在就自动使用。对项目内自动登记、latest 与查询长期生效的明确顺序，可在对应 `scan_sources.json` 来源条目配置 `"delivery_order_ids": ["id_new", "id_old"]`，必须无重复且完整覆盖当时所有交付；之后有新交付时要更新配置。模块复用现有 Library 锁与原子替换，拒绝将输出覆盖 Delivery、软链接或写入 RAW 来源内部。

CLI 和 Web API 共用 `LibraryDataQuery`。`data-query --kind history` 按文件查看所有交付出现；`data-query --kind history-at --vendor V --library L --view LEF --path lef/core.lef --delivery-id REAL_ID --work /path/to/work` 返回该交付及此前最近一次出现的记录和定位路径；API `/api/library-data` 使用相同参数（参数名 `delivery_id`）。这只是按交付历史选择，**不是 EffectiveVersion 的采纳结果**；没有身份确认的文件也不能自动进入旧检查器。按索引选中的 `delivery_id/file_id` 可供现有 `facts` CLI 等明确消费，后续 CheckResult 需依原检查流程显式运行。

查询会将已保存索引与归档 Delivery 和当前确认顺序核对；不可用、未更新或不一致时回退到已归档记录，不猜测顺序，也不在页面读取时写回索引。`index_status` 指出 `VALID`、`MISSING`、`STALE` 或 `INVALID`。

`data-query --kind logical-history --vendor V --library L --view LEF --file-key KEY --work /path/to/work` 合并同一库、同一 View 下**身份已明确确认**的跨路径文件，候选和未知身份仅计入未确认数量；同一交付有多个已确认同名身份则报错。`index-status` 和库页面提示过期状态；若发生“交付已写入、索引未更新”的中断，读取不会隐式写盘，后续自动登记或显式索引构建会在现有库锁内恢复。无法确认顺序或索引与历史冲突时需要人工核验。

`facts-at --work ... --runs ... --vendor V --library L --delivery-id ID --view LEF --path LEF/a.lef --out facts.json` 可按确切的旧版 Delivery 记录解析文件，不要求调用者自己查找 `file_id`；系统只复用归档中真实、唯一的 ID，仍验证路径和分类。单独的 `raw.simple.v1` 若没有真实 `file_id`，当前 `file_facts.v1` 无法表达其来源，不能通过该入口伪造 ID，也不能声称已支持其直接生成现有检查结果。Fact 仍需通过现有 CheckResult/Excel 流程消费，`facts-at` 不会隐式执行检查。

## 性能与边界

当前原型的安全校验会读取所有已归档 Delivery，并重建旧索引用于对照；`APPEND` 只向投影插入新增出现，但总体仍随历史规模增长，尚未验证生产级性能，也没有跳过全部旧 JSON 的增量保证。无 SHA-256 检查 RAW 内容；不能用历史索引证明 RAW 路径当前可访问或内容未变化。测试目录 `exports/file_index_validation_20261119/` 使用原型提供的模拟交付，首次 `REBUILD`、第二次 `UNCHANGED`，7 个不同路径、9 次出现。示例采用 `--trust-delivery-order` 仅用于模拟，不意味着生产顺序已确认。

补充微基准：100 个内存模拟交付、每个 200 条文件记录（共 2 万次出现）在当前环境构建约 0.016 秒，已存在索引的完整校验约 0.021 秒。此测量不包含读取 JSON、文件系统写入、锁争用或生产数据，仅用于核对算法规模，不能代表端到端性能。
