# 脚本架构与遗留代码审查

审查日期：2026-11-21。范围：当前 `ai_lib_qor` 工作目录的源码、设计文档及工作目录。以用户后续确定的路径式 Delivery、Formal、Effective、file_index 和 FileFacts 为现行数据方向；blackbox v3.1 保留其职责分层与插件思想，旧字段和旧目录细节不自动视为现行要求。

## 结论

目前是新旧两条链路并存的过渡状态：新链路已有命令行、路径式数据和检查报告；统一查询、可扩展插件编排、历史能力迁移和性能还没有收敛。不能认定完全符合目标架构，也不能仅因文件名有 v2、v3、compat 就删除。

## 路径式主链

```text
RAW / Formal NL 总目录
  → sources/root_inventory.py → Delivery / Formal + latest 软链接
  → application/minimal_effective.py → Effective + latest 软链接
  → application/minimal_file_index.py → file_index.json
  → application/minimal_facts.py + facts/parsers.py → FileFacts
  → application/minimal_checks.py → CheckResult
  → reporting/excel.py、reporting/overall_excel.py → 单版本 / 整体 Excel
  → workbench/path_app.py 展示；CLI 可直接调用各新入口
```

有效版本初始化和更新是单独操作，扫描不会自动完成 Effective 演化。更新使用明确的 `set` / `remove`，相同成员集合不会重复发布；默认从 Formal 初始化时，不传成员筛选则使用符合条件的全部链接。整体检查目前以 SourceLibrary 的多个有效版本为范围，不等于跨库 BusinessIP 聚合。

| 职责 | 实际脚本 | 判断 |
|---|---|---|
| CLI | `cli.py`、`__main__.py` | 新旧命令集中共存，新命令多以 `minimal-` 开头。 |
| 盘点与产物 | `sources/root_inventory.py`、`layout.py`、`timestamps.py` | 负责来源扫描、生成和链接；与应用索引层直接耦合。 |
| 有效版本 | `application/minimal_effective.py` | 有初始化和明确文件操作；新链暂无完整的预览、排除、历史组合恢复流程。 |
| 文件索引 | `application/minimal_file_index.py` | 从三类来源构建和校验路径历史，查询时重新构建比对，不是增量查询。 |
| 文件事实 | `application/minimal_facts.py`、`facts/parsers.py`、`facts/_compat/` | 新格式、复用现有解析器；Verilog/CDL/SPICE 为部分解析。 |
| 检查 | `application/minimal_checks.py`、`checks/plugins/` | 直接调用部分插件，未接入旧的注册器与统一编排。 |
| 输出 | `reporting/path_workbook_model.py`、`excel.py`、`overall_excel.py` | 两类 Excel 共用新检查链；整体范围是单库有效版本。 |
| Web | `workbench/path_app.py`、`workbench/app.py` | 两套工作台共存；路径式页面直接调用新应用服务。 |

## 对照要求和风险

1. **统一查询未完成。** `application/data_query.py` 的 `get_check_context()` 属于旧查询模型；路径式检查从索引和有效版本自行选择。Web 也有自己的索引读取和组装逻辑。应在新契约上提供共同的查询与检查上下文。
2. **插件边界未打通。** `checks/registry.py`、`runner.py`、`plan.py` 和 `assembler.py` 仍存在，但 `minimal_checks.py` 直接导入 LEF 检查插件、硬编码选择和组合；增加检查不能只注册插件。
3. **两套索引冲突。** 旧 `file_index_v3.py` 与新 `minimal_file_index.py` 输出文件名都为 `file_index.json`，结构不同；新刷新会拒绝覆盖不兼容格式。应明确版本和迁移入口，不能互相覆盖。
4. **性能和真实变化检测未闭环。** 根目录盘点使用 `os.walk`，索引查询重新构建核验；重复运行不重写不等于增量扫描。路径不变的 RAW 内容修改无法由七字段清单本身发现；按需解析会读取文件并计算摘要。
5. **契约校验不统一。** 已有 `delivery_minimal.schema.json`、`file_facts_path.schema.json` 和 `check_result_path.schema.json`；当前路径式 Formal、Effective、file_index 使用代码内规则，未看到与当前格式对应的完整独立 Schema。
6. **业务能力仍有迁移缺口。** 新路径式流程的自动演化、排除、恢复、跨库 BusinessIP 和丰富检查规则尚不等同于旧流程；不能以旧版功能存在声称新链已经支持。
7. **分层依赖需整理。** `sources/root_inventory.py` 在生成后调用应用层索引刷新；`minimal_effective.py` 又依赖来源模块的指针函数。业务操作、扫描和发布编排的边界交叉。
8. **工作台选路有风险。** `workbench/app.py` 可依据工作目录自动选择新旧应用，`is_path_work()` 用交付文件和 evidence 的存在情况判断；混合目录不宜把自动识别当作可靠的契约版本识别。
9. **配置分散。** 新工作台保存 `work/path_sources.json`；路径索引的无日期版本登记时间读取 `work/scan_sources.json`；旧 Formal 同步还使用 `work/formal_sources.json`。CLI 新盘点入口接受显式来源参数，不能假定所有入口共用同一配置。

## 脚本保留与候选分类

### 新链和共享代码：保留

`application/minimal_*.py`、`sources/root_inventory.py`、`sources/layout.py`、`sources/timestamps.py`、`facts/parsers.py`、`facts/_compat/`、`checks/plugins/`、`reporting/excel.py`、`reporting/path_workbook_model.py`、`reporting/overall_excel.py`、`versions/store.py`、`workbench/path_app.py`。`facts/_compat/` 被新解析器直接引用，`versions/store.py` 的锁、原子写入和校验被新链使用；不能整体删除旧目录。

### 旧链仍在调用：迁移后再决定退役

`application/data_query.py`、`file_index_v3.py`、`v3_checks.py`、`effective_workflow.py`、`effective_publisher.py`、`library_runs.py`、`pipeline.py`，以及 `sources/auto_ingest.py`、`classifier_adapter.py`、`formal_sync.py`、`delivery_builder.py`、`snapshot_builder.py` 等由旧 CLI/Web 继续使用。`checks/registry.py`、`runner.py`、`plan.py` 等是旧编排组件，也可能作为迁移设计参考。`workbench/app.py` 和其旧页面仍有旧工作目录路由；不能在新链未覆盖其能力和历史数据前删除。

旧 `lib_guard` 不要求维护，但旧分类/发现/Formal 同步仍存在对它的导入；`source_discovery.py` 中的部分版本识别辅助函数被新盘点复用。迁移前必须按具体引用拆分，不能笼统删整个旧包。

### 历史参考：标注版本，不作为当前规范

`design/blackbox_v3_1/` 中的设计 Markdown、旧版 schema、早期架构图和带日期的旧文档是历史设计或旧契约证据。它们的模块化思想可参考，但其中旧身份字段、旧目录和旧执行流程已被后续需求部分取代，应加适用版本说明。`exports/`、`archive/` 和 `work/` 是历史样本或运行数据，并非废弃脚本；需单独核对用途和保留要求，不列入自动删除。

实际 `work/libraries/` 仍有 `evidence_delivery_*.json` 和旧式 `delivery_*.json`；因此旧身份并未从全项目及旧工作目录清除。迁移需要保留来源证据并先产出可核验的新工作目录，再决定历史数据处置。

## 建议的收敛顺序

1. 明确当前契约版本与新旧工作目录的显式选择；补齐路径式 Schema、时间和排序规则及配置说明。
2. 把新路径式成员选择收敛到统一查询及 CheckContext，单版本和整体报告消费相同输入快照。
3. 迁移有效版本预览、排除和恢复语义，同时保留不可变历史；补齐真实库与模拟库核验。
4. 将路径式事实适配插件协议，恢复注册、计划、执行和结果汇总，按检查逐项验证旧功能而非直接复用旧身份。
5. 引入可核验的增量扫描与索引策略；原位修改的检测证据独立于七字段 Delivery。
6. 对每个旧命令建立「替代入口、历史读取、结果一致性、调用方、测试」清单；全部通过后按模块退役，而非先删代码。
7. 更新 README、契约文档和架构模型，明确历史文档与现行入口；页面调整放在数据链路稳定之后。
