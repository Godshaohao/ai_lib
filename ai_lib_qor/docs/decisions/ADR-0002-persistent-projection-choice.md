# ADR-0002: Catalog 持久化查询投影的实现选型

- 状态：PROPOSED（尚未授权实施）
- 日期：2026-11-18
- 范围：LibraryCatalog/Query Service 的性能和共享查询状态

## 背景

多 HTML 页面需要频繁查询统一的对象、来源、版本和运行历史。当前 JSON 读取和投影是否具有实际瓶颈尚未获得本地生产规模测试。外部 HPC/NFS 部署也会影响存储选型。

## 候选方案

| 方案 | 优点 | 限制 |
|---|---|---|
| A. JSON + 进程级缓存 | 改动最小 | 多进程失效、启动重建、常用聚合耗时需测量 |
| B. 持久索引文件 / 预计算视图 | 易部署，可重建 | 查询灵活度和增量一致性需自行管理 |
| C. SQLite 只读投影 | SQL 查询、关系索引、事务一致性 | 需迁移/重建机制；多进程/NFS/WAL 条件需评估 |
| D. 集中式 DB | 多客户端写读和部署隔离 | 运维复杂度高，当前未见必要证据 |

## 决策门槛

- 典型来源数量、文件数、版本数、页面并发、请求耗时实测。
- 确定单/多进程写入位置、目录所在文件系统类型和备份策略。
- 确定增量处理后的投影一致性版本号，失败恢复和重建流程。
- 明确 SQLite 是**可重建查询索引而非独立权威业务真相**。
- 获得明确任务授权后实施；遵守根 AGENTS.md 的“不未经要求引入数据库”。

## 当前决定

**暂不选定任何具体数据库。** 优先稳定 Query API 和共享语义，评估真实性能后再确定。此 ADR 不应被 Codex 解释为立即新增 `catalog/store.py` 或 SQLite schema 的指令。
