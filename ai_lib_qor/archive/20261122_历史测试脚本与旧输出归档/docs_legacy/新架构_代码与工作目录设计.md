# ai_lib_qor 新架构：源码与工作目录设计草案

> 2026-11-13。根据用户给出的 Vendor → SourceLibrary → BusinessIP → Revision 目录、v3 契约设计及 v5.1 实施门槛整理。以下是**拟议结构**，不是已经实现的程序或真实数据。新源码采用独立的 `src/ai_lib_qor/`，不以旧 `src_qor` 的目录和脚本布局作为新架构。

## 1. 目标

工程师先找到供应商、来源库和业务 IP，看到该 IP 的有效版本，以及每次检查的文件变化和质量结果；有需要时可追溯到供应商的交付文件或公共正式 NL 快照。

系统分别记录：交付中出现了什么、正式库链接了什么、有效版本选用了什么、检查发现了什么、人工采纳了哪个版本。多个计算过程可以共同形成一次检查结果；正式检查结果由同一发布入口写出。

## 2. 新项目结构（提案）

```text
ai_lib_qor/
├── src/
│   └── ai_lib_qor/                  # 新源码，拟新增
│       ├── cli.py                   # 接收命令、参数，调用具体用例
│       ├── config.py                # 读取和核对登记、归属、交付顺序配置
│       ├── sources/
│       │   ├── raw_scanner.py       # 发现一次 RAW 交付及其文件
│       │   └── formal_scanner.py    # 盘点正式 NL 链接与实际目标
│       ├── parsers/
│       │   ├── lef.py               # 提取 LEF 的 Macro、Pin 等事实
│       │   └── liberty.py           # 提取 Liberty 的 Cell、Pin 等事实
│       ├── versions/
│       │   └── composer.py          # 前版完整成员 + 明确的本次变化 → 新 Rev
│       ├── checks/
│       │   ├── content_diff.py      # 比较选定文件的内容
│       │   ├── lef_diff.py          # 比较 LEF 的 Macro / Pin 事实
│       │   ├── lef_liberty.py       # 核对指定 LEF 与 Liberty 的关系
│       │   ├── evidence.py          # 核查来源、证据、覆盖及测量依赖
│       │   └── assembler.py         # 合并本次检查，形成一份 CheckResult
│       ├── storage/
│       │   ├── paths.py             # 按业务 ID 定位 work/ 下的产物
│       │   └── publisher.py         # 校验后发布固定记录并更新入口
│       └── reporting/
│           ├── view.py              # 从选定 Run 组织只读展示数据
│           ├── html.py              # 生成 HTML
│           └── excel.py             # 生成 Excel
├── config/                          # 用户维护的登记、归属和顺序
├── schemas/                         # v3 七类契约设计；正式使用前确认权威版本
├── tests/                           # 对应模块及合同、证据和增量用例
├── docs/                            # 设计与使用说明
├── work/                            # 运行时生成的数据，结构见下
└── pyproject.toml                   # 项目元信息与运行入口（拟新增）
```

以上是职责划分草案，文件名不代表代码已经存在。第一阶段只需覆盖明确的 LEF 差异和 LEF–Liberty 检查；目录不要求一次性实现所有能力。是否引入新依赖、哪些检查支持可运行实现，应在实际开发时根据输入与验收确定。

## 3. `work/` 业务数据结构（提案）

```text
work/
├── vendors/
│   └── vendor_a/
│       └── libraries/
│           └── library_x/
│               ├── deliveries/
│               │   ├── delivery_v07.json       # 一次交付的文件清单
│               │   └── delivery_v08.json
│               ├── delivery_checks/            # 可选：针对交付的预检查
│               │   └── <delivery_id>/
│               │       └── run_001.json
│               └── ips/
│                   └── rtavfs/
│                       ├── effective/
│                       │   ├── index.json      # 最新计算 / 当前已采纳指针
│                       │   ├── versions/
│                       │   │   ├── rev_007.json
│                       │   │   └── rev_008.json
│                       │   └── acceptance.jsonl # 可选：真实采纳事件
│                       ├── checks/
│                       │   └── rev_008/
│                       │       ├── run_001.json
│                       │       └── evidence/   # 可选：检查的可追溯证据
│                       │           └── run_001/
│                       └── reports/            # 可选：由选定 Run 生成
│                           └── rev_008/run_001/
│                               ├── report.html
│                               └── report.xlsx
├── formal_nl/                                  # 公共正式来源，不按 IP 复制
│   └── NL2.5.3/
│       ├── index.json                         # 拟议：正式快照查询入口
│       └── snapshots/
│           ├── snap_0001/
│           │   └── snapshot.json
│           └── snap_0002/
│               └── snapshot.json
├── file_facts/                                 # 文件实例的解析事实
│   ├── facts_core_v07.json
│   └── facts_core_v08.json
└── staging/                                    # 运行期间的临时片段
    └── <job_id>/
```

`delivery_v07.json`、`delivery_v08.json` 和 Rev 编号是目录示例。供应商版本可以重复交付，真正身份使用唯一 `delivery_id`，不能单靠 `v08` 文件名区分；重交的命名规则在实际登记和路径合同中确认。`delivery_checks/`、`evidence/`、`reports/` 与 `staging/` 是组织方式建议，不是额外的权威业务契约。没有采纳事件时不必创建 `acceptance.jsonl`。

`formal_nl/<formal_nl_id>/index.json` 是独立的**拟议正式快照查询入口**，与 `ips/<ip>/effective/index.json` 的有效版本及采纳指针职责不同。它不是新增的权威业务事实；字段、选取范围、顺序、更新与重建规则尚待确认。正式快照仍按 `formal_snapshot.v1` 合同表达；本目录从 v3 示例的 `snapshots/<snapshot_id>.json` 改为 v5 也展示过的 `snapshots/<snapshot_id>/snapshot.json`，因此读写路径与历史示例解析需要适配，不表示 Schema 字段已修改。

跨 SourceLibrary 的 IP 仅保留一个权威 Rev 位置，成员通过来源库、交付及文件行的固定引用关联。没有 BusinessIP 的来源库，沿用 v3 草案在 Library 下维护 `effective/` 的方案；其最终位置仍需项目确认。

## 4. 七类数据及写入职责

| 业务产物 | 工作目录 | 主要产生过程 | 主要作用 |
|---|---|---|---|
| DeliveryRecord | `vendors/.../deliveries/*.json` | RAW 扫描和登记 | 一次交付实际有哪些文件 |
| FormalSnapshot | `formal_nl/.../snapshots/<snapshot_id>/snapshot.json` | 正式链接盘点 | 某时刻正式来源的固定状态 |
| FileFacts | `file_facts/*.json` | 对指定文件做格式解析 | 保存解析范围、对象和来源 |
| EffectiveVersion | `ips/.../effective/versions/rev_*.json` | 版本组合 | 完整成员和相对父版的变化 |
| CheckResult | `ips/.../checks/<rev>/run_*.json` 等 | 内容 / LEF / Liberty 检查及汇总 | 本次变化、质量结论和证据 |
| AcceptanceEvent | `ips/.../effective/acceptance.jsonl` | 实际人工或授权决定 | 追加采纳、回退等事件 |
| EffectiveIndex | `ips/.../effective/index.json` | 根据已存在的记录更新 | 当前版本查询入口，可重建 |

一类契约可有多份记录；临时片段、报告和索引视图不能自行成为第二份业务权威。图示的写入职责为拟议设计，v3 七份 Schema 是否即项目正式权威合同仍需确认。

## 5. 一次检查的数据流

1. 从 `config/` 读取已确认归属及交付顺序；扫描后形成交付或正式快照。
2. 根据明确的文件归属和选择，组成完整 Rev。新交付不会自动等于已采纳版本。
3. 从本次目标锁定来源文件及所需解析事实；按需执行内容比较、LEF 差异、LEF–Liberty 检查。
4. 不同检查的结果先放在内存或暂存目录；核查输入身份、证据及覆盖，汇总为一份检查结果。
5. 校验已确认的 v3 Schema 和业务关系；成功后才发布 `run_001.json`，并按该结果生成 HTML / Excel。
6. 人工采纳或回退才追加采纳事件并更新相应指针。检查或报告更新不会自动修改有效版本。

RAW / Formal NL 来源、最新计算 Rev 与当前采纳 Rev 可以各自不同。`PASS` 需要实际证据和明确检查范围；未检查、覆盖不足或证据不可信不得表现成整体通过。

## 6. 实施前待确认

1. 工作区七份 v3 Schema 是否就是该新项目的正式合同；v5 合成示例与 v3 Schema 已知不能直接互换。
2. 重交时 `delivery_id`、文件名与交付顺序如何确定；`PARTIAL` 是否可映射为 `INCREMENTAL` 需按实际包语义核实。
3. 正式快照 `index.json` 的字段、范围、顺序、更新和重建规则；`work/` 的 evidence 形态、结果与真实文件关联、生产路径及权限；现有 v5.1 门禁原型仍存在 Gate 依赖检查缺口。
4. LEF / Liberty 解析的真实覆盖范围、单位和异常行为；缺失事实保持未知。
5. 生成器、检查结果与 HTML / Excel 的一致性验收方式；首版采用受影响检查重跑，不假设自动缓存有效。
