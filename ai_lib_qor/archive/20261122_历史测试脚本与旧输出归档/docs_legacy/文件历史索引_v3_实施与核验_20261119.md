# file_index.v3：实现和核验

`file_index.v3` 是单库可重建查询投影，权威记录仍是 Delivery、FormalSnapshot 和 EffectiveVersion。每条路径各自保存 RAW 实际出现、Formal 历史链接观察和 Effective 全集采用三条时间线；每条时间线的顺序分别来自已确认交付顺序、Formal 父子链和 Effective 父子链。不要把来源变化等同内容变化或人工采纳。

## 读取、刷新和兼容

`ai_lib_qor file-index-refresh --work WORK --vendor VENDOR --library LIBRARY` 在现有库锁内从归档 JSON 重建投影并原子替换，结果可为 `REBUILD`、`MIGRATE_V3`、`APPEND`、`UNCHANGED` 或 `ORDER_UNCONFIRMED`。`APPEND` 表示新投影保留了旧事实并增加数据，并不代表低复杂度增量：目前会读取并重建整个归档投影。`data-query --kind index-v3` 返回现算的投影和已保存索引状态；一般查询只读，失效时回退归档记录。已有的 `python -m ai_lib_qor.application.file_index` 是旧 v2 独立工具；请勿将其 `--rebuild` 输出指向 v3 索引。

自动交付登记、明确登记、Formal 同步、新 v2 Effective 发布及扁平 v1 Effective 索引重建后，在同一库锁内尝试刷新。源记录已发布但刷新失败时不回滚源记录；查询状态为过期或不可用，必须检查错误后恢复。索引不会修改 RAW、NL 或不可变历史，不能提供跨文件事务。旧 v2 索引在所有已有 RAW 行与归档一致时可原地转换；旧索引损坏、历史缺失、父子链分叉或引用不唯一时停止覆盖。

## 关联语义

- 同库 RAW 引用必须可通过真实 Delivery ID 或唯一归档别名解析，并落实到真实文件行；alias 不写成真实交付 ID。
- 旧分类 `RESOLVED` 不等于逻辑身份已确认。没有明确确认依据时 v3 RAW 行的 `file_key` 为 `null`；路径、文件 ID 和分类仍保留。逻辑查询和逻辑比较只合并已明确确认且唯一的身份，其余使用精确路径。
- Formal 关联要求归档引用唯一、文件行匹配，并且快照的 `resolved_path` 与归档 RAW 根路径及相对路径文本一致；不一致或中间软链接导致无法离线确认时放入 `unmatched_formal`，保留原 `source_match` 和引用线索。即便文本一致，也只是**归档记录相符**，不是重新读取当前软链接或比较内容。多跳链接可能被保守放入未匹配区。
- Effective 使用完整 Rev 成员；跨库来源附 `source_scope`、`source_path`，不伪装成本库 RAW。缺交付、不唯一或父版本缺失时不发布不完整索引。每个 `files[path].raw` 只包括本库真实出现；跨库节点可能没有本库 RAW 出现。
- `compare-revisions-logical` 只在双方都明确确认且同一来源范围的 `file_key` 一致时按逻辑身份匹配；其他情况按 View + 精确路径，输出 `NOT_CHECKED`。旧 `compare-revisions` 原路径语义不变。

## 样例与限制

`exports/file_index_v3_review_20261119/` 是隔离验收副本：2 次交付、5 个 View、7 个路径、9 条 RAW 出现；1 份 Formal 快照中 4 条归档匹配、3 条未匹配；2 个 Effective Rev 各 7 个完整成员，共 14 条。V06 是模拟 Delivery；Formal 是历史快照，未对模拟目录重新观察；示例顺序显式配置，仅适用于样例。两次刷新分别为 `REBUILD`、`UNCHANGED`。

现有检查与 Excel 仍消费各自的 FileFacts/CheckResult 和检查计划；这个索引尚不能自动推导完整检查计划或取代既有插件，也不应凭 Formal 来源关系给出检查 PASS。旧 v1 Effective 成员如无法映射到唯一 RAW、或旧共享 Formal 无法唯一归属，无法发布完整 v3，需先修正来源记录。生产规模性能与实际生产 RAW/Formal 当前链接仍需单独验收。
