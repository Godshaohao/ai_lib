# 业务闭环实施进度 · 2026-11-20

实施基线为 c1f845f；当前工作目录不是 Git 工作树，另有先前的未提交页面修改。此文为阶段记录，不表示整个规格已验收。

## 当前实现

- 按归档 Delivery 的显式身份和已确认顺序，预览已有 v2 有效集的增量更新。父版本必须全部能映射到已确认身份；未知身份、中间未处理交付、业务 IP 新文件归属不明均停止并返回 NEEDS_REVIEW。
- 以完整父版本继承，确认相同 file_key 时替换来源；改名只保留新路径。UNKNOWN 交付缺项不删除；显式删除需要在父版本中唯一定位。重复采用的交付不创建空版本。
- 新增 CLI `effective-preview` 与 `effective-apply --expected-parent`；自动登记新交付后尝试各已存在的 v2 有效集，不构造不存在的 IP 或初始集。
- 用户此前明确要求发布后自动生效。新工作流在既有 AcceptanceEvent 中以 `actor=automatic` 追加 ACCEPT；旧 publish_v2 调用的默认行为不变。该事件不表示检查通过，也不是人工确认记录。
- 输出目录、file_index.v3 与既有契约保持兼容；索引刷新失败且版本已发布时返回 PUBLISHED_INDEX_STALE。原始历史不覆盖。
- 归档中同一 View 的已确认身份重复时报错；未确认身份仍不参与逻辑合并。

## 未完成

- 已支持按有效集排除或恢复交付，策略写入 scan_sources.json 的 excluded_delivery_ids；库目录 runs.jsonl 记录操作请求。发布时在库锁内再次检查排除策略。当前有效版本仍引用被排除交付时会报告影响，但不修改旧版本。
- 已支持采纳回退及基于历史文件组合创建新版本，分别由 acceptance-rollback 和 effective-restore 命令执行；Web 库页面支持恢复文件组合及采纳回退。恢复操作校验来源可访问、排除冲突及父版本。
- 排除策略只能修改 scan_sources.json 中显式配置的来源；从 Library Map 推导但未显式配置的来源需要先写入来源配置。操作审计在配置更新前写入请求，若配置写入失败，该日志只证明请求，不证明成功。
- 首次 RAW/Formal 初始化还需要已有 CLI 显式操作；不明 IP 新文件不能自动归属。当前未实现人工决策界面、严格身份配置新入口。
- 单版本与整体检查共用内存 CheckContext；index-v3 查询返回已核验的发布索引，避免一次查询重复构建。首次一致性验证仍完整重建归档投影，轻量 freshness 和检查文件自动配对尚未实施。
- 所选 LEF/Liberty 的 FileFacts 可跨运行复用，存放于 Library 目录；复用键包含来源范围、文件身份、解析器版本和实际选中文件的内容摘要。并非全库扫描，且缓存命中不证明历史交付字节一致。新 v3 检查的 CheckResult、Excel、HTML 和运行日志集中在对应 Library 目录，不再生成 input_plan.json；Web 兼容读取历史 runs。旧非 v3 计划执行、扫描与 Formal 观察仍使用原运行目录。
- 检查前后对归档元信息进行一致性检测；检测到变动时拒绝输出 CheckResult。该检查不是归档内容的密码学完整性保证。
- 自动 ACCEPT 与历史人工采纳事件可通过 actor 区分；自动事件在发布中途失败时可能留下已发布版本和需要修复的派生索引，必须先核验再继续，不宣称事务性完成。历史文件组合恢复检查文件存在与路径范围，不证明当前内容与历史字节一致。
- 尚未对真实 RAW/Formal 进行本次端到端验收，也未做规格要求的性能基线和完整 Excel 人工验收。
