# 七类契约与统一查询层

`work/` 和 `runs/` 中已有记录是数据来源。`LibraryCatalog` 只读取这些记录，在内存中组织查询结果，不生成新的业务契约、不扫描 RAW，也不调用解析器或检查器。

入口：[library_catalog.py](../src/ai_lib_qor/application/library_catalog.py)。

| 接口 | 回答的问题 | 主要来源 |
| --- | --- | --- |
| `refresh()` | 重新读取哪些已保存记录？ | 来源配置、DeliveryRecord、FormalSnapshot、EffectiveVersion、EffectiveIndex、AcceptanceEvent |
| `overview()` | 已知哪些来源库、IP 和正式来源？有哪些扫描观察？ | 已保存来源和索引，`runs/` 中的观察记录 |
| `library_detail(vendor, library)` | 某库有哪些交付，以及文件位最新、次新出现在哪里？ | DeliveryRecord，按交付顺序组织 |
| `formal_detail(nl_id)` | 正式快照链接到哪些 RAW 文件，哪些 IP 的有效版本引用了这些来源？ | FormalSnapshot、DeliveryRecord、EffectiveVersion |
| `ip_detail(vendor, library, ip, revision_id=...)` | 指定版本包含哪些文件？相对基线和已有检查结果如何？ | EffectiveVersion、EffectiveIndex、DeliveryRecord、FormalSnapshot，以及可匹配的 CheckResult |

同名文件位的最新和次新是**出现记录**，不是内容是否相同的判断；若该文件位的交付顺序重复，则不推断最新和次新。Formal 来源仅在记录引用能唯一对应交付文件时归属供应商和库；无法唯一确定时显示未知或不唯一。IP 关系只使用有效版本中有证据的文件引用，不按文件名猜测。相同 NL 和快照 ID 出现多次时，查询层标记冲突，不按其中一条推断归属。

检查结果只有在目标、基线、版本内容、文件来源和运行记录能够对应时才显示；对应关系不等于已验证 RAW 内容新鲜度。没有 FileFacts、CheckResult 或采纳事件时，仍可查看已保存的库和交付；不会因此伪造检查或采纳状态。

Web 的全局、库、Formal NL 和 IP 页面使用同一查询层。查询层每次刷新从已保存 JSON/JSONL 重建，**目前不提供持久内存服务、增量索引或 SQLite 缓存**；页面请求会重新读取相关记录。若数据规模造成明显性能问题，应先测量，再考虑可从记录重建的缓存。

单次重建内，同一交付记录只读取并校验一次；全局视图一次读取各扫描和 Formal 观察并按来源分组，不再针对每个库重复读取全部观察。缓存只在一次 `refresh()` 中有效；重新刷新重新读取记录，不用 RAW 内容哈希作为变化依据。这不是跨进程缓存，也不保证并发写入期间所有 JSON 属于同一事务快照。

可从 `ai_lib_qor/` 运行只读检查：

```bash
export PYTHONPATH="$PWD/src:$PWD/../src${PYTHONPATH:+:$PYTHONPATH}"
python -m ai_lib_qor catalog-refresh --work /path/to/work --runs /path/to/runs
python tools/benchmark_catalog.py --work /path/to/work --runs /path/to/runs
python tools/benchmark_catalog.py  # 临时生成合成数据，不写业务目录
```

`catalog-refresh` 在进程中构建目录并打印统计，不会留下数据库文件；如果权威记录不可读取而产生警告，输出 `PARTIAL` 并返回非零状态。扫描和登记由单独的 `scan` 命令完成。

当前 IP 目录中的 IP 来源于已有有效集索引。项目尚无经过核实的独立业务 IP 名单和跨库映射，不能从交付文件名自动宣布 IP 归属。原有检查计划和文件事实准备能力也没有因本次查询层调整而变成全自动。
