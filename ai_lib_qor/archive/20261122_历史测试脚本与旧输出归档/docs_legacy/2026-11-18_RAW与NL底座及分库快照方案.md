# RAW 交付与 Formal NL 底座：最少确认和分库快照

状态：方案；尚未实现。已确认：正式快照按 NL 阶段、Vendor、来源库三者分别维护历史。本文中的配置与目录仅是拟议接口，不表示现有程序已支持。

## 目标与边界

RAW 来源形成 DeliveryRecord，Formal NL 的链接观察形成 FormalSnapshot；两者均保存可追溯证据，供 CLI、有效版本、检查、Excel 和 Web 共同消费。扫描观察、可信身份、完整范围和采纳是不同事实。RAW 和 NL 保持只读，旧记录不可覆盖；快速扫描不要求 SHA-256。

## 分库方案

推荐方案：对一个 NL 根目录只盘点一次，按链接实际目标与已登记的 RAW 文件唯一匹配，归入 `(formal_nl_id, vendor_id, source_library_id)`，每组保存独立快照和父版本链。一次同步同时汇报无法归属、目标失效、多个候选的链接，不将其强行放进任何库。一库的问题不应阻挡其他库的可确认文件，但不能因为未归属链接被排除就声称该库范围完整。

备选方案是继续使用 NL 全局快照，在查询时按来源库过滤。它兼容当前目录，但所有库共享历史和发布条件，无法独立追踪每个库的变更；不满足已确认的历史隔离要求。另一种是为每个库重复扫描同一个 NL 根目录，逻辑直观但扫描成本随库数量增长；不推荐。

建议持久化目录，具体路径为拟议而非当前实现：

```text
work/formal_nl/<NL>/libraries/<Vendor>/<SourceLibrary>/
  snapshots/<snapshot_id>/snapshot.json
```

不改写原 `work/formal_nl/<NL>/snapshots/`。新的快照 ID 在同一个 NL 内全局唯一，以维持现有 `formal_nl_id + formal_snapshot_id + file_id` 引用的唯一性。查询层须同时识别新旧目录，并按三元组选择最新快照；旧全局快照没有明确 Vendor 归属时标记为旧范围，不能猜测其所属库或混入某库的新历史。目录名必须校验和限制在工作区内，不能通过符号链接或路径穿越越界。

沿用 v3 FormalSnapshot 字段，`scope.source_library_ids` 仅含该来源库；Vendor 通过所属目录、配置及唯一的交付引用核实。由于 v3 的 `source_ref` 本身不含 Vendor，若多个 Vendor 使用同一个 `source_library_id` 且引用不能唯一解析，必须报告歧义并阻止可信关联；不能仅凭库名认定。完整性判定需明确库的 NL 覆盖范围、所有未归属链接的影响及扫描是否完整；不能证明完整时记 `PARTIAL`。当前 builder 将空文件位视为未匹配，按路径可确认来源与确认逻辑文件位应分别表示；若 v3 无法准确承载，先保留观察及异常，不伪造 `MATCHED_RAW` 或变更 Schema。

快照创建前后复核链接路径和目标；相同链接集合、范围及引用时复用该库上一快照。仅证明链接关系未变，不证明目标文件字节未变。未知、冲突、失效链接和目录链接单独列出，不自动推断删除。

## 最少人工配置与确认

| 时机 | 人需要提供或确认 | 自动处理与限制 |
| --- | --- | --- |
| 首次配置每个来源库 | Vendor、来源库 ID、RAW 根目录和版本目录规则；有可靠版本顺序来源时配置 | 按规则自动发现版本。规则无法确定的版本保留待确认；登记顺序不能冒充供应商版本顺序。 |
| 首次配置正式库 | NL 阶段、正式目录，以及允许纳入的 Vendor/来源库范围 | 单次扫描 NL；唯一实际路径关联到已登记 RAW 时自动归库，多候选和未知来源单独报告。若某库本就不应出现在此 NL，需由范围配置明确。 |
| 首次建立文件身份 | 每库确认可复用的文件位映射规则或明确映射；涉及 Liberty 的 corner、mode 等按实际命名约定配置 | 规则可跨版本复用；不能只因为文件名唯一就把业务身份视为人工确认。没有证据的文件保留未知，可显示 View 候选但不能用于冒充已确认文件位。 |
| 每次新交付 | 只有业务需要完整替换、删除或准确时间顺序时，确认供应商依据、包类型、作用范围和顺序 | 无证据时 `package_mode=UNKNOWN`、范围未确认；发现缺失不视为删除。已配置且无冲突的来源与规则无需逐文件反复确认。 |
| 出现例外 | 确认重复候选、同名跨库、失效或未登记目标、文件位冲突、规则不适用、同路径原地修改等异常 | 只列异常，不让人工逐条确认所有正常文件；不覆盖历史，变更需重新观察和留痕。 |

BusinessIP 只有在可信名单或明确映射存在时归属；Vendor / 来源库、View 与 BusinessIP 不是同一个判断。相同大小和修改时间不证明内容相同；需要可重现字节时应使用不可变来源或另行明确内容校验策略。用户此前要求的快速扫描默认不计算文件内容 SHA-256。

## 配置建议

现有程序已经使用 `work/scan_sources.json` 和 `work/formal_sources.json`；前者已有来源、版本路径规则、显式 `file_mapping` 和 `delivery_orders`，后者配置 NL ID 和根目录。当前的 `file_mapping` 主要是具体路径，不能假设跨版本规则已可运行；当前 `formal_sources.json` 也不能配置本方案的按库范围。

推荐沿用现有两个配置文件扩展，而不是引入第二份互相竞争的来源真相：RAW 中每库增加经确认、可复用的相对路径规则；Formal 中每个 NL 增加允许的 `(vendor_id, source_library_id)` 列表。精确字段和兼容校验在实施时确定，规则必须检查同一交付内文件位冲突，并将规则版本和命中依据写入现有证据。示意：`NL2.5.3 → [IHP/sg13g2_stdcell, SRAM22/sram22_256x16m8w8]`。此处不是可直接运行的配置。

## 实施影响与验收

1. 先增加可复现测试：两个 Vendor 同名库、多个库分链；一个库未知不阻挡另一个库的有效部分；同一库链接不变复用，变化只追加该库历史；空位、冲突、断链与范围不完整不伪装成功。
2. 改造来源同步与 builder，保持观察和快照语义分离；复核 v3 Schema 与跨记录引用，保留旧数据，覆盖并发写入及链接在扫描中变化的情况。
3. 更新 Catalog、CLI、版本/报告引用及 Web 的快照选择；验证旧全局历史仍可读取，但不会误作某库的最新快照。
4. 在隔离工作目录使用多库模拟 RAW/NL 跑通扫描、登记、分库快照、复用和变更；只读核对公开真实样本，不修改真实来源和既有业务记录。核对 Schema、按库归属、父链、完整性标记和界面异常信息。

已知实际测试基线见 [Delivery 与 Formal NL 数据构建审查](2026-11-18_delivery_nl_review.md)：5 库 21 份交付、182 条文件中有 78 条尚未解析；39 条正式链接都能按路径找到 RAW，但其中 15 条没有文件位。现有 104 条 `RESOLVED` 均来自文件名候选，并非人工确认。这个现状不能称为业务分类已经确认。
