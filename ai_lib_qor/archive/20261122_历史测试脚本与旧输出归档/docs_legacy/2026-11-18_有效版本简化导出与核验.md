# 有效版本简化导出与核验

## 事实核验

`exports/flat_library_review_rdyp0zdh` 是模拟工作目录。该目录的 `delivery_005.json` 内部权威 `delivery_id` 为 `delivery_fe93387faa824ebbb7bdcf451b83e56c`，其 `rev_0001` 引用的是同一 ID 和其中 LEF 的 file_id。简化 RAW 输出将文件名 `delivery_005` 用作别名；因此这是同一目录中两个表示方式，并非找不到关联。不能把其他独立测试目录里的相同名字当作同一交付。

该 Delivery 有七个文件：LEF 及三个 Liberty 为文件名推断候选，GDS、SPICE、Verilog 文件位未解析。`rev_0001` 实际成员为一份 LEF；`rev_0002` 在此基础上增加一份 Liberty FF。历史记录可以证明所保存的成员，不能反推出当时测试操作选择这些文件的完整意图，更不能凭文件存在推定另外五个文件被纳入或采纳。

## 新的只读投影

`data-query --kind simple-effective` 基于已保存 Revision 和关联 Delivery 生成 `effective.simple.v2`，`v2` 与已有另一种结构的 `effective.simple.v1` 区分。包含所有者、Revision、父版本、创建时间、`sources`（真实 RAW 版本 → Delivery 别名）和按 View 分组的 `views`（RAW 相对路径 → 版本）；Liberty 按 NLDM/CCS/ECSM 等子组组织。Formal 初始化基准在 `formal_baseline` 保留快照 ID。当前实现要求同库且版本唯一；缺失来源、跨库、同版本对应多个交付、重复路径均拒绝导出，不能静默猜测。记录不会扫描 RAW 或将投影写回历史。

```bash
PYTHONPATH=src:../src python3 -m ai_lib_qor data-query --kind simple-effective \
  --work <work目录> --runs <runs目录> --vendor <供应商> --library <库> \
  --owner <有效集所有者> --revision rev_0001
```

`exports/effective_simple_review_20261118/` 中的两个 JSON 是从模拟历史生成的派生样例；不是新的已采纳版本。V05→V06 的七文件继承只是附件中的假设，当前没有据此伪造历史。

## 边界与后续工作

新格式目前是只读导出，不是新的权威有效版本契约；现有 `versions` 服务、索引、检查、Web 和报告仍消费 `effective_version.v1` 的 `members`、`changes` 等。已有简化 `build_effective` 使用 `effective.simple.v1`，没有切换成 v2。要完全实现附件的持久化替换，还需设计 v2 Schema、版本发布与继承、Formal 基准、跨库/重复版本身份、删除与重命名语义、v1/v2 历史读取、索引/采纳、Web 和报告消费的迁移，并实测跨格式历史；在这些工作完成之前不得把只读导出称为全面迁移。
