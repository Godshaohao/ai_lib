# 增量协作与设计审查

> 基于 v3 示例和 v3.1 黑盒方案；本文件及相关 `.py.md` 均为设计，未实现生产行为。这里的“增量维护”有两种不同含义：**本轮汇总时逐步贡献**，以及**下轮生成新历史版本**。

## 1. 一份检查 JSON 如何由多个脚本共同形成

以 v3 的 `rev_0002` 与 `rev_0001` 为例：

1. `plan.py` 固定检查目标、基线、需要检查的文件来源、facts 引用、profile 与参数。检查插件不能自己扫描和决定最新版本。
2. `content_compare.py` 确认同一 `file_key` 的旧/新来源，并提供来源变化；有足够证据时才提供内容判断。
3. `lef_macro_diff.py` 读取同一文件两侧 facts，贡献 `MAC_A.SIZE` 从 `[120,80]` 到 `[124,80] um`、Pin C 出现等对象变化。
4. `lef_liberty_pin_match.py` 读取所选 LEF 与 tt Liberty facts，贡献仅覆盖信号 Pin 名称和方向的质量结果。
5. `assembler.py` 将各片段按固定比较对和对象身份归并，填写 v3 `file_changes`、`quality_checks` 与 `summary`；将结果交给证据校验与统一发布入口。
6. 得到的 `run_001.json` 示例完整内容在 [assembler.py.md](src/ai_lib_qor/checks/assembler.py.md)；三个插件的输入范围、输出片段分别位于插件设计文件。

插件贡献是内存结构或暂存片段，不是独立业务契约。字段未贡献、明确 `null`、`UNKNOWN` 是三件事。相同字段出现不可调和的明确值时拒绝合并；一个插件没填某字段不属于冲突。`quality_checks` 的插件实例需要兼顾 scope：相同插件可能针对多个 LEF/Liberty 配对；实例键与 v3 `check_id` / `scope_file_keys` 的精确规则尚需确认。

## 2. 七类记录的更新与协同

| 记录 | 协同输入 | 汇总与写入 | 下次变化 |
|---|---|---|---|
| DeliveryRecord | 扫描文件、分类、已确认的范围/顺序 | `delivery_builder` 组装；Publisher 发布 | 新交付 ID → 新记录；不能覆盖旧交付 |
| FormalSnapshot | 链接盘点、来源匹配、覆盖范围 | `snapshot_builder` 组装；Publisher 发布 | 确认状态变化 → 新快照；单靠链接文字无法证明内容未变 |
| FileFacts | 同一来源的解析器及属性提取 | `facts_assembler` 组装；Publisher 发布 | 新来源或解析器变化 → 按已确认身份/版本策略新事实；v3 的多解析器溯源能力待确认 |
| EffectiveVersion | 父版全集、文件选择、已确认交付规则 | `composer` 组装；Publisher 发布 | 成员来源变化 → 新 Rev；旧 Rev 保持不变 |
| CheckResult | 文件比较、对象差异、跨 View 插件 | `assembler` 合并；证据/Schema 校验；Publisher 发布 | 规则或相关输入改变 → 新 Run；不改旧 Run 或 Rev |
| AcceptanceEvent | 有授权的人工或业务决定 | `acceptance` 构造；事件写入入口追加 | 每次真实决定追加一行；检查 PASS 不自动采纳 |
| EffectiveIndex | 已发布 Rev 与可重放采纳事件 | `index_projector` 计算；Publisher 更新 | 指针可更新；重放、排序、并发与崩溃恢复规则待确认 |

公开的示例 `formal_nl/.../index.json` 是用户要求的拟议快照查询入口，**不是** v3 `effective_index.v1`；其格式没有被本设计虚构为已确定契约。

## 3. 本轮审查发现与处置

| 优先级 | 发现 | 当前处理 / 待确认 |
|---|---|---|
| P1 | 原脚本文件多为单行摘要，缺少字段、格式及示例 | 34 份脚本补充对应 v3 字段与中文含义；七个主要产物组装/写入脚本加入完整合成示例 |
| P1 | 插件协作缺少具体合并过程 | 为三个插件补充临时贡献 JSON，并在 assembler 给出同一 `run_001` 的归并步骤；禁止直接改写历史结果 |
| P1 | v5 贡献结构与 v3 正式结构不同 | 对字段来源、目标及限制加以标识；不能改版本字符串冒充兼容；插件版本、参数和完整证据无损存储方式待确认 |
| P1 | 随包验证器将 `CHANGED` 限定为必须有 `object_changes` | 该条件位于 `tools/validate_examples.py` 的示例跨记录验证，不是 Schema 的字段约束；纯字节变化无对象差异的处理需人工确定，不编造变化 |
| P1 | v5.1 Gate 证据检查有伪造依赖反例 | evidence 设计中要求校验上游检查、指标、上下文与可用性；仍未实现或验证 |
| P2 | v3.1 的路径与用户此前要求不同 | 保留用户提出的 Vendor/IP 和 `formal_nl/<NL>/index.json` 形式；多有效集及 formal 索引字段待确定 |
| P2 | 多解析器共同维护 FileFacts 的身份和字段归属缺少规则 | 要求同一固定 source_ref、对象键和字段归属；v3 单 parser 元数据无法表达完整多解析器来源时停止无损发布并提出扩展 |
| P2 | “单一写入者”无法单独保证崩溃安全 | 明确临时写入、冲突、幂等和事件重放方向；文件系统锁和跨文件恢复尚无实现证明 |

## 4. 真实信息与示例边界

术语和 116 条字段解释来自 v3 的文档确认表；真实 JSON 示例逐字复制自 v3 合成数据。插件贡献是为了说明协作关系提出的**非权威中间格式**。Schema 允许的结构、文档提出的业务规则、以及示例验证器的额外断言需分别核实；不得因为示例通过就宣布真实库或生产数据已验证。
