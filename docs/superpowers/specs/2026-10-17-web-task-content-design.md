## 1. 目标与范围

- 目标用户：登记库、检查新版本、核对差异和交付链接的工程师。
- 主要判断：本次操作针对哪个对象、已有结果是否足够、执行后会修改什么。
- 输入：现有目录、版本、扫描、对比、组合、发布及任务数据。
- 输出：任务表单、可追溯结果入口、文件清单和明确的执行反馈。
- 边界：沿用现有后端与 Release Gate，不增加流程引擎、数据库、审批角色或第二套质量判断。

本轮使用 pd-vibe-guard 的需求与实现边界审查，以及 ui-ux-pro-max 的层级、渐进展开、表单与反馈原则。
用户明确以桌面为主，验收尺寸使用 1440 × 900；不以移动端布局为目标。

## 3. 产品判断

当前页签切换、文件筛选、任务日志与表单保留可继续复用。主要问题是不同动作作用范围混在同一个“当前版本”背景下，以及同一信息在多个位置重复出现。

| 维度 | 当前判断 | 依据 |
|---|---|---|
| 找到操作 | 基本可用 | 扫描、对比、文件对比、技术检查均有独立页签 |
| 知道操作对象 | 未达标 | E1 可复现 |
| 理解执行前提 | 未达标 | E3 无基准仍可执行整组差异检查 |
| 设置的可预期性 | 未达标 | E2 跨页字段共同保存 |
| 信息密度 | 仍需收紧 | E4 固定区过高，版本角色、扫描状态和建议反复出现 |
| 结果可追溯性 | 有基础，未完整验收 | 现有任务提供日志和报告入口；本轮没有新建质量任务或真实发布 |

不以测试数量换算“9 分”。本轮是单库、双版本的专家走查；多用户、50 版本、任务失败恢复和真实发布尚不在本轮已验证范围内。

## 4. 设计选择

| 方案 | 优点 | 代价 | 决定 |
|---|---|---|---|
| 继续缩字、加折叠 | 变更最小 | 对象不一致与隐藏保存范围依旧存在 | 只作为局部手段 |
| 保留现有导航，按当前动作组织输入和结果 | 复用代码，解决对象、参数、反馈的对应关系 | 需要调整几个表单和局部状态 | 采用 |
| 全部改成强制步骤向导 | 顺序直观 | 无法便捷重跑对比、单独检查文件或盘点外部正式目录 | 不采用 |

## 5. 页面结构

沿用三个一级页签和设置入口。扫描、对比、文件对比等仍可独立使用，不要求依次执行。

| 区域 | 默认展示 | 按需展开 |
|---|---|---|
| 左侧库目录 | 搜索、源库/已发布切换、库名、版本数、一个需处理状态 | 类型、厂商、平台等筛选 |
| 顶部工作条 | 库名、版本选择、当前任务一行状态 | 完整版本表、日志详情 |
| 库与版本 | 已登记库表、发现路径、候选确认表 | 手动登记、发现限制、登记表维护 |
| 版本分析 | 操作页签、该操作的对象与参数、一个主要执行按钮、结果入口 | 高级参数、人工备注编辑、原始日志 |
| 发布交付 | 交付对象、目标绝对路径、目录名、链接方式、预演结果、发布按钮 | 有效组合编辑、多库清单对比、强制发布 |
| 设置 | 工作区目录、扫描默认值、发现默认值，分别可见且分别保存 | 高级限制、异常维护 |

顶部只固定紧凑工作条。完整版本表保持入口在顶部，但展开内容参与普通滚动，不把整张表持续钉在屏幕上。
主操作区按“对象 → 参数 → 执行 → 结果”排布。保留文件结构和变化清单，放在操作区之后；不重复造一份检查结果面板。

## 6. 对象与状态设计

### 6.1 每个动作明示作用范围

| 动作 | 必须在执行按钮附近显示的对象 |
|---|---|
| 扫描 | 库、目标版本、原始目录 |
| 版本对比 | 基准版本 → 目标版本 |
| 深度文件对比 | 旧文件绝对路径 → 新文件绝对路径 |
| 技术检查 | 实际所选组合及其组成版本、可选对比组合 |
| 确认有效组合 | 完整包 + 按顺序排列的增量包 |
| 发布 | 本次实际交付对象 → 目标绝对路径 |

技术检查第一阶段明确标为“检查组合”，选择器直接列出组成版本，内部组合编号作为次要信息。
其选项可以独立于顶部版本保留，但必须把实际对象清楚显示在表单与任务结果中。不能用顶部版本名代替真实检查目标。
若以后加入直接检查单个原始版本，应单独实现 raw 输入契约与测试；不能把任意候选组合冒充该版本，也不能为了打开表单自动构建候选。

### 6.2 本版检查与版本差异

- 单对象规则在没有基准时可运行。
- 只适用于差异的规则明确标出“需要基准”，未选基准时不作为可执行项。
- 若整个方案只有差异规则，直接在基准字段下显示“选择基准后可检查这些变化”。
- 混合方案支持只执行可用规则，并明确列出本次未执行的项目。
- 保留既有结果状态；任务完成、质量通过、检查不完整分别表达。

### 6.3 设置作用范围

- 操作表单保留“仅本次”的覆盖参数。
- 设置页展示独立的默认值草稿，不从另一页不可见的临时表单中取值。
- “保存目录”“保存扫描默认值”分别提交对应范围。若接口必须接受完整对象，则用已加载默认值合并当前分组，不能读取无关临时字段。
- 提供字段级变更提示即可；不增加统一审批弹窗或新的配置平台。

## 7. 表格、文案与结果

版本表主列：版本、包类型、扫描、对比、发布、操作。基准可显示在对比单元格，减少“角色 / 事实结论 / 下一步”的重复列。
用户备注有内容时优先显示；没有内容时只保留“添加备注”入口。

| 当前用词 | 设计用词或处理 |
|---|---|
| 正式库（指登记后的原始库） | 已登记库 |
| 正式发布库 / 正式目录 | 已发布库 / 正式发布目录 |
| 证据状态、事实已就绪 | 扫描完成、对比完成；未验证范围另列 |
| 接入窗口、pending window | 普通操作页不显示；必要时使用待处理版本 |
| snapshot_*、effective_id | 组成版本为主，编号放详情 |
| lef_all 等自定义方案名 | 显示可配置的中文名称；无名称时保留原 ID，不猜含义 |
| 已结束 / PASS | 明确区分任务完成与检查结论 |

技术检查结果仍以文件交付：任务区域提供“检查摘要（Markdown）”“详细清单（JSON）”和完整日志，不在页面平铺原始检查结果。
发布预演必须先显示新增链接、替换链接、同名冲突、保留/跳过数量及明细入口，实际发布按钮紧邻这份结果。
目录不存在、权限不足、同名冲突等属于具体错误；展示路径、原因、可执行处理办法，避免只显示“任务失败”。

## 8. 最小实施顺序

1. 修正技术检查的作用范围展示、组合名称和无基准规则选择；验收请求对象与用户看到的对象一致。
2. 分离本次参数与默认配置草稿；验证只保存目录不会改变扫描默认值。
3. 压缩固定工作条，将版本表移出持续固定区域；发布输入放在动作之前。
4. 收敛重复状态与机器术语；同步现有验收文档，删除过期说明。

第一阶段主要涉及 `web/static/app.js`、`web/templates/index.html`、`web/static/styles.css` 与行为测试。
若需要补充组合组成或方案显示名，只在 `web/semantic_actions.py` 的展示响应中提供明确来源的数据；执行逻辑、parser、事实结构和 Release Gate 保持原合同。
